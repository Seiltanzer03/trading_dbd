## Оставшиеся пакеты — фиксированный порядок

| ID | Объём | Конечный результат и остановка |
| --- | --- | --- |
| P1 | Регулярная официальная FOMC-доставка: bounded off-host acquisition, publication/receipt/materialization/revisions, exact-SHA доставка после выпуска, фактическая просрочка | Рабочая доставка и честная измеренная регулярность. Объявлять опрос каждые 10 минут можно только после реальных последовательных доставок через подходящий scheduler; GitHub cron сам по себе этого не доказывает. Отказ/просрочка явны, TTL не расширяется ради green. |
| P2 | Макро/событийные прогнозы на уже утверждённых источниках | Сохранённый до события consensus и историческая причинная выборка, модель, доступный прогноз и вклад; либо конкретный отсутствующий вход/сигнал не найден. Без consensus не подменять surprise текстовой новизной. |
| P3 | Межрыночные и сессионные модели | Синхронные реальные данные, проверенная identity/mapping, календарь/DST и конечный существующий набор моделей/горизонтов. По каждому включённому инструменту пригодный прогноз или явный отрицательный/недостаточный результат. |
| P4 | Поток заявок / ликвидность | Реальные последовательные наблюдения разрешённой площадки и модель эффекта/издержек; proxy не назван брокерным CFD стаканом. Нет пригодного источника — фиксируем недоступность и закрываем пакет с этим ограничением. |
| P5 | Позиционирование и value/carry | Реальные CFTC/OI/потоки с датой доступности и проверенным mapping; фактические условия executing broker с единицами. Неполученные carry/quotes остаются null, расходы не дублируются. |
| P6 | Опционные физические прогнозы и неподдержанные identity | Конечная калибровка на доступной выборке, отдельные Q/P и подтверждённый proxy. Crypto/JPY100 включаются лишь при достаточных реальных входах; повторный поиск без новых данных не запускается. |

Опционный сбор и накопление точных баров продолжаются фоново по существующему
контракту. Это не разрешение открыть дополнительную ветку разработки или
считать завершённым P6. Набор инструментов берётся из конфигурации; не добавляем
новые инструменты/семейства/действия внутри этих пакетов без изменения плана.

После **каждого** пакета обновляем фактическое состояние цепочки:
источник → историческая выборка → обученная модель → доступный прогноз →
фактический вклад. Это отображение готовности, а не требование получить модель
в инфраструктурном P1 или при отсутствующем входе. Недоступные звенья остаются
UNAVAILABLE/null с причиной; отсутствие сигнала — отдельный результат конечного
поиска. Матрица и конечный отчёт обновляются только по новым доступным результатам. Сравниваем HOLD, действующий контроль, стартовые схемы и отключение
компонентов: net result, CVaR10/хвосты, издержки, вмешательства, отмены и вклад.
Observed replay, модельные сценарии и prospective решения публикуются раздельно.
Не вызываем LLM повторно ради строк ablation. Не подбираем веса до желаемой прибыли.

## Глобальный G.1-план: измерение отдельно от полномочий

| Линия | Следующий этап | Условие / предел |
| --- | --- | --- |
| G.1E.2 | Bounded/materialized runtime | Существующая штатная готовность, без request-time тяжёлого исследования |
| G.1S / G.1S-T | Реальные короткие горизонты и пользовательские сделки → shadow → OOS | Existing gates: raw ≥120, effective N ≥60, positive/negative ≥20, ≥3 дня; сделки — отдельная relevance выборка |
| G.1C → G.1D | Native expiry option-Q → purged Q→P OOS | Native expiry не сокращается; raw ≥200, effective N ≥100, classes ≥30, ≥3 периода, >1 expiry cluster и отсутствие critical contract errors |
| G.1-M / G.1-M.1 → OOS | Полная траектория менеджмента и отдельная локальная диагностика | Локальная польза 15/30/60/120m не заменяет терминальный результат сделки |
| G.2 | Отдельное решение о policy promotion | Не входит в P1–P6; research/shadow не получает автоматически production/auto-execution/promotion authority |

Гейты G.1 не ослабляются ради завершения технического пакета. Если выборка не
готова, этап имеет статус COLLECTING/EVIDENCE-GATED, а разработка пакета
заканчивается с явным ограничением. Не ждём доказанной прибыльности каждого
семейства, но и не выдаём обученную модель за разрешённую торговую политику.

## Проверки, выпуск и контроль объёма

1. Перед пакетом фиксируем scope, существующие входы и criterion. Изменение
   поведения воспроизводим профильной регрессией и исправляем владеющий слой.
2. Один integrator принимает diff; независимое review конечного пакета.
3. Один обязательный полный CI на final revision. Новый diff требует проверки
   изменённой области; одинаковые тяжёлые задания без причины не повторяем.
4. После разрешённого merge: automatic deploy → readiness → smoke → public
   HTTP → exact-SHA необходимые публикации. Dispatch success не равен delivery.
5. Пакет заканчивается после этого результата и публикации ограничений.

Новый источник, модель, экран, оптимизация, новый action или ослабление gate
не добавляются по ходу. Попутная находка записывается в отдельный backlog;
в текущий diff входит только дефект, мешающий его согласованному criterion.
Изменить этот перечень и порядок может пользователь отдельным указанием.

## P1: текущая рабочая граница

Первая часть P1: автоматический exact-SHA FOMC refresh после успешного HTTP smoke
и read-only status фактического возраста/просрочки относительно 600s target.
Capture admission TTL остаётся 3600s и показан отдельно от cadence target.
Первый свежий capture означает WITHIN_TARGET, а не доказанную непрерывную доставку.
Отсутствие новых statements между заседаниями не освобождает от проверки доставки.

Проверены scheduled runs: `37479305663`, `37521386399`, `37546108504`,
`37562322759`: интервалы многочасовые при cron каждые десять минут.
GitHub документирует задержку/пропуск schedule events:
https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule
Поэтому **регулярность P1 остаётся открытой**, пока нет независимого off-host
scheduler и реальных cadence receipts. Не создаём облачные ресурсы/новые права
из предположения, что S3-переменные также дают права на cloud scheduler.
Новый scheduler оформляется одной конечной частью P1; расширение источников
в этот пакет не входит. Ручной dispatch не считается доказательством регулярности.
